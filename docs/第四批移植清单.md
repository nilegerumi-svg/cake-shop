## 一、动手前先证明「改了会生效」

前两批踩过「数据挂上了、主程序读的是自己那份」的坑（第二、三批的
`__TM_STATE_GET__`）。本批先坐实取数链，才动手：

| 检查 | 结论 |
| --- | --- |
| bundle 内联了 `baseCost:45` 等字面量 196 处 | 是，但那是配方书/图鉴用的 `kk`/`Dk` 等数组 |
| `.baseCost` 属性**读取**点 | 仅 3 处：定价 `customPrice`、随机事件售价、寿司摊隔夜结算 |
| 这 3 处从哪取 | **全部走 `ge[e.recipeId].baseCost`** |
| `ge` 是什么 | bundle 顶层 `ge = window.Cake.RECIPES_GAME`，**引用赋值** |
| 加载顺序 | `index.html`：`js/data/index.js` → `js/app.bundle.js`；bundle 首个分片 `app-01.js` 第 2 行即 `await window.__cakeDataReady` |

结论：数据层装载完毕 → 本批覆盖 `RECIPES_GAME[id].baseCost`（**原地改属性**）
→ bundle 才执行 `ge = window.Cake.RECIPES_GAME`，拿到的就是覆盖后的表。
**所以必须原地改属性，不能替换整表**——否则 `ge` 会指向旧对象。这一点写进了
`js/data/index.js` 的注释里，防止后人改错。

| 文件 | 动作 | 说明 |

| `js/data/recipes/v53_pricing.js` | 新增 | 126 项 `{ id: 新 baseCost }` 映射，挂 `Cake.RECIPE_BASECOST_V53` |

`9256d6022210…`）、`js/app.bundle.js` 与 12 个分片、加载器、`css/`、

覆盖逻辑只做三件事：只覆盖**已存在**的配方、只改 `baseCost` **一个字段**、
缺项计数上报。删掉 `v53_pricing.js` 与那段接线即可完整回滚到原价——这也是
选「独立补丁」而非改大文件的原因：仓库上一轮拆分的成果原样保留，可单独开关。

## 三、明确不纳入：scone / tiramisu 的整配方重构

第三批清单提到的「零散差异」查清了，是 `scone` 与 `tiramisu` **两个 id 的
整体重构**，不是调价：

| 字段 | `scone` 仓库 → v53 | `tiramisu` 仓库 → v53 |
| --- | --- | --- |
| `ings` | `{butter:1,eggs:1,flour:2,milk:1}` → `{butter:2,flour:2,milk:1,sugar:1}` | 多加 `cheese:2` |
| `category` | cuisine → snack | cuisine → cake |
| `taste` | — | bitter → creamy |
| `shelfDays` | 1 → 3 | 2 → 3 |
| `unlockCost` | 160 → 110 | 400 → 260 |
| `bakeCost` | 8 → 10 | 13 → 16 |
| `emoji` | 🫓 → 🫖 | — |

这改的是配方本体、烘焙行为和保质期，会连带影响食材消耗与品控，风险远大于
改一个价；而且与第三批搬入的 `scone_cuisine` / `tiramisu_cuisine` 是**不同 id**。
本批只跟进你拍板的定价，这两道整体重构单独留作候选，交你定夺。

### 一处如实更正（我自己的测试脚本 bug）

第一次跑验证时，抽样里出现 `banana_bread=70`（看似没被改）。原因是脚本在测
「引用是否同一对象」时把它改成 1074，复原时**硬编码写回了 70**，把补丁后的
74 覆盖了——是测试污染了数据，不是补丁失效。已删掉那段会写值的探针，改成
纯读取，重跑确认 126 项全对。这里记下来，免得后人看到旧输出误判。
