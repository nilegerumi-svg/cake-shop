# 已知问题与修复记录

这份文档记录移植与逆向过程中**实际验证过**的缺陷、修法与判定依据，以及一批"看着像 bug、实际是原设计"的现象。目的是让后面接手的人不必重新踩一遍。

判定口径统一为三条：

1. **能复现**：给出具体操作路径或存档状态；
2. **有依据**：能从原压缩包、v53 离线版、或数据表之间的一致性推出"这是错的"；
3. **不越界**：改的是移植接缝与数据，不去"改良"原版设计。

## 一、已修复

### 1. 配方列表与运行时字典不同步（第三批新菜做不出来）

**现象**：第三批移植补进来的 8 道 v53 新菜（腰果奶油蛋糕、花生酥、杏仁曲奇、马卡龙、核桃面包、开心果冰淇淋、英式司康、提拉米苏）在 `Cake.RECIPES_GAME` 里都在，数据、食材、价格齐全；但打开「厨房 → 制作工坊」，列表里一道都看不到，玩家只能看不能做。

**根因**：配方书与制作列表渲染用的是**编译期静态常量** `RECIPES_ALL`（`js/src/npc/recipes-mashed-potato.js`，由 `RECIPES_BAKERY_ALL + RECIPES_DRINKS + CUISINE_RECIPES_ALIAS` 拼成，共 186 道），而不是运行时的 `RECIPES_GAME`（255 道）。移植只往字典里加了数据，没有同步这张静态清单。

**修法**：把 `RECIPES_ALL` 从字面量改成 IIFE，在原三张表之后追加"字典里有、静态表里没有"的条目。过滤条件三条，缺一不可：

- 跳过 id 带命名空间前缀的（`cake:` / `dish:` 共 56 条，属另一套菜单数据，见下节）；
- 跳过 `ings` 为空的（7 个装罐成品 `*_jar`，走加工台不走烘焙）；
- `category` 必须已经在原表里出现过，避免把莫名其妙的东西并进来。

只追加、不改原有顺序，因此原有 186 道的展示次序不变。

**验证**：修补后 `RECIPES_ALL` 由 186 → 194；8 道新菜全部出现在列表；实测烘焙成功并产出成品（一次 2 件，符合 `BAKE_SIZE_OPTIONS` 的产量）；「甜品大师」成就的分母同步变为 194，与实际可研发数一致。

### 2. 符号还原改了定义、没改引用（进游戏直接落错误边界）

**现象**：点「开始经营」后不渲染主界面，而是「游戏出了点小问题 — `gi is not defined`」。

**根因**：逆向阶段做「压缩名 → 语义名」时，`PanelFrame` 等 9 个符号只改了定义处，引用处仍是旧短名。这些组件都只在**进入游戏后**才渲染，而当时的校验脚本只等到 `#root` 有子节点就判通过（标题页本身满足），所以一直没暴露。

| 旧引用 | 实际定义 |
|---|---|
| `gi` | `PanelFrame` |
| `dF` | `AchievementPanel` |
| `Sf` | `FireflyLayer` |
| `Z6` / `e8` / `t8` | `ParkActivityPanel` / `FishingPanel` / `NewspaperPanel` |
| `Z0` / `W0` | `MilestonePanel` / `AchievementList` |
| `xF` / `pF` / `gF` | `observeThemeChanges` / `broadcastTheme` / `sendFrameCommand` |

**修法**：按语义把 9 处引用改回已定义的名字。**教训**：所有 `js/src` 模块拼接后共享同一作用域，改名必须跨文件全局做（工具 `eslint-scope` 遍历 `globalScope.through`），单文件改名必然漏改引用。

**验证**：校验脚本加固为「点开始经营 → 断言错误边界未触发 → 断言 iframe 面板已创建且内部 `#root` 有内容」。

### 3. 时间推进单位错位（一次加工只花 1/60 的时间）

**现象**：加工台做一次「熬酱」标注 30 分钟，实际游戏时间只走 30 秒。

**根因**：`advanceHours(state, hours)` 收的是**小时**，但有 3 处传了 `TIME_COST.x / 60`（把分钟又除了一次 60）。

| 位置 | 原写法 | 修正 |
|---|---|---|
| `shop/03` 加工 | `advanceHours(o, TIME_COST.process / 60)` | `advanceHours(o, TIME_COST.process)` |
| `night/02` 中等烘焙 | `advanceHours(u, TIME_COST.bakeMedium / 60)` | 同上 |
| `night/02` 海边玩 | `advanceHours(o, TIME_COST.coastPlay / 60)` | 同上 |

同函数内 `consumeSatiety(u, o / 60)` 的 `/60` 是**对的**（饱食度按分钟扣），两套单位混在一处，极易看错。

**验证**：加工一次后游戏时间 +0.5 小时（=30 分钟），精力扣除不变。

### 4. 第三批新配方的 10 种坚果食材缺失（数据在、料不到）

**现象**：8 道新菜里有 6 道要用腰果粉、花生、花生粉、杏仁粉、核桃、核桃粉、开心果粉，但 `INGREDIENTS_GAME` 里一个都没有，永远是「食材不足」。

**根因**：第三批只移植了配方，没有把 v53 离线版里的 10 个坚果/坚果粉条目与 5 条磨粉加工配方一并带过来。

**修法**：

- 新增 `js/data/ingredients/nuts_v53.js`，从 v53 离线版原样提取 10 个条目（id / name / emoji / price / shelfLife / season / category / desc）；
- 在 `js/data/index.js` 里于 bundle 读取 `INGREDIENTS_GAME` **之前**并入（时序很关键，晚一步 bundle 就拿不到）；
- 在 `js/src/shop/fishing-allergen.js` 的加工配方数组末尾补 5 条磨粉配方（`p_grind_*_powder`），并在 `js/src/a11y/processing-baking-sections.js` 的加工白名单里加入这 5 个 id，否则加工台不显示。

**验证**：物品桥 445 → 455；加工台出现「磨花生粉」等 5 项；实测磨粉成功，原料 -1、成品 +1。

### 5. 加工函数里 `c` 的作用域断裂

**现象**：加工完成后产物进不了食材袋（静默失败，无报错）。

**根因**：`processIngredient` 里 `const c = INGREDIENT_MAP[a.out]` 声明在 `if (!a.packOnly) { ... }` **块内**，函数末尾却在块外引用 `c`。原始压缩码逐字如此，属原包自带缺陷。

**修法**：把 `if (!a.packOnly)` 的判断下沉到使用处（`c && ...` 改为先取映射再判断），使变量提升到函数作用域。改动最小，语义等价。

**验证**：磨粉后 `ingredients.peanut_powder` 正常 +1，并记入 `seenIngredients`。

### 6. `.btn-gray` 没有样式定义（白字透明底，按钮文字看不见）

**现象**：2F 的「💡 灯已开 / 🌙 关灯」、床铺互动等处，按钮只有描边、文字几乎与背景同色，看不清（夜间模式下更明显）。

**根因**：`.btn-chunky` 基样式的最后一项是 `color:#fff`，本身**不设背景**；各色变体（`btn-brown` / `btn-yellow` / `btn-green` / `btn-blue`）各自补 `background`，唯独 `btn-gray` 在本包 CSS 里**没有任何定义**，于是落到"白字 + 透明底"。全包共 7 处用到 `btn-gray`。

**修法**：在 `css/game/01.css` 与 `css/frame-base/01.css`（同一份样式的两个入口分片，内容逐字相同）的 `.btn-brown` 之后补一条：

```css
.btn-gray{background:#efe3cf;border-color:#c9b59a;color:var(--brown-dark)}
```

**验证**：截图对比，灯开关与新增的「🌙 睡到明早」文字均恢复可读；`btn-chunky:disabled` 的 `opacity:.45` 仍然生效，禁用态照样看得出来。

## 二、看着像 bug、实际不是

排查时最容易误判的几类，逐条给出判断依据，省得下次再查一遍。

| 现象 | 判断 |
|---|---|
| 配方表里有 7 个 `*_jar` 条目 `ings` 为空 | **设计**。它们是加工台的装罐产物，由 `processIngredient` 直接写入，不参与烘焙，因此没有食材清单。 |
| 56 条 id 带 `cake:` / `dish:` 前缀的配方 | **另一套数据**（餐馆菜单命名空间），不是重复导入。价格统一 30、`ings` 用的是旧 id（`flour_low`、`chicken_egg`）。它们不进 `RECIPES_ALL`，因此不出现在任何列表；`RECIPE_RUNTIME_DATA` 只按 id 单查，也不会被遍历渲染。保留原样。 |
| 「英式司康」在烘焙与料理两个页签各出现一次（`scone` / `scone_cuisine`） | **原设计**。两者 `category` 不同（甜点 vs 料理），价格与配方也不同（72 / 59）。v53 离线版里两者本就并存。 |
| 每天睡醒精力只恢复到 98 → 90 → 82 | **设计**。精力恢复量 = `MAX_ENERGY × (0.55 + 0.45 × health/100)`，而健康每天固定 -5；若当天没睡（`sleptToday <= 0`）再 -12。点「下一天」属熬夜开天，不吃「已睡」标记，所以连掉。真睡觉走 `sleep` 动作会置标记。 |
| 「一觉睡到明早」醒来精力是 98 而不是 100 | **设计**。这条路径的恢复系数是 `0.9 + 0.1 × health/100`，健康 100 才是满值；健康 75 时约 97.5 → 98。比「下一天」（`0.55 + 0.45 × health/100`）高一大截，且必定视为「睡过」，不吃 -12 惩罚。 |
| 鱼饵 `bait_*` 价格 0 | **设计**。鱼饵不零售，靠任务与采集获得。 |
| 15 条配方 `unlockCost` 为 0 | **设计**。初始配方（迷你戚风、椰子蛋糕等）免费解锁。 |
| `pages/fate/index.html` 存在但从不加载 | **死目录**。底部「通讯」页签的 `onClick` 是打开手机 App（`if (g.id === "fate") return a()`），`active: e === "fate"` 恒为 false，`PanelFrame` 因此永不创建该 iframe。保留不影响运行，删掉也不影响，暂留。 |
| 存档 `coins` 为负不归零 | **设计**。允许欠债，靠后续营业还。 |

## 四、审计脚本的误判规则（避免复查被噪声干扰）

旧版 `audit2/3/5` 跑出来一大堆"问题"，逐条核实后**全是误报**。现已合并为 `audit_clean.py`，结果分两级：`❌ 真实缺陷`（确实断链/数值倒挂/数据不可用）与 `ℹ️ 设计预期`（合法但可疑）。下面这些"看着像 bug"的项已被脚本显式排除，复查时不要再当缺陷：

| 现象 | 实际 | 排除依据 |
|---|---|---|
| NPC 关系指向不存在的 NPC（110 条） | `rels` 是**关系描述文本**（"许小满的父亲""中医馆老中医"），不是 NPC id | 脚本不再对 `rels` 做 id 校验 |
| 商店商品指向不存在物品 | 把 `SHOP_CONFIG.name="烘焙街角商店"` 这个**店名**当成了物品 id | 只校验 `SHOP_ITEMS`，不扫 `SHOP_CONFIG` |
| 家具材料 `nail/paint/cloth/glass/glue` 不在食材表 | 家具走独立的 `MATERIAL_MAP`（17 种）；`INGREDIENTS_MATERIALS` 只含 `wood/iron/parts` | 家具材料对照内嵌的 17 个材料 id 校验 |
| 7 个 `*_jar` 配方无任何食材 | 装罐成品，由"装罐"动作消耗库存生成，本就不写 ings | 排除 id 以 `_jar` 结尾者 |
| 15 个配方 `unlockCost` 为 0 | 初始免费配方 | 当作设计预期，不报错 |
| 重名配方（如 `scone`/`scone_cuisine`、`tiramisu`/`tiramisu_cuisine`） | 同名异版，v53 既有设计；配方按 id 检索，同名不冲突 | 排除命名空间配方，其余降级为提示 |
| 5 个鱼饵 `price=0` | 鱼饵不零售 | 排除 `category:"bait"` |
| `wood/iron/parts` 的 `shelfLife` 非正 | 材料表条目用 `tags:['material']` 标记，本就不定义保质期 | 排除无 `shelfLife` 或带 material 标签者 |
| 命名空间菜单（如 `dish:braised_beef`）食材种类 >8 | 餐馆菜肴本就多料 | 排除带 `:` 命名空间的 id |

> 仍保留生效的 ERROR 级检查：NPC 喜好断链、SHOP_ITEMS 断链、成就/任务/节日/种子引用断链、售价倒挂（`baseCost ≤ bakeCost`）、非鱼饵食材 `price≤0`、非材料 `shelfLife≤0`、配方食材 >8 种。这些若真出现断链会照常报警——脚本是"降噪"不是"静音"。
| pageerror / console.error | 0 / 0 |

## 五、已接通的遗留系统（bundles 材料补给包）

`js/data/bundles/` 里的 4 个材料包（`BUNDLE_BASIC/CHOC/FRUIT/PRO`）此前只被聚合进 `window.Cake.BUNDLES`，**全代码零消费逻辑**——属于"移植带进来但系统没做"的半成品。现已接通为可玩系统：

- **购买动作** `buyBundle(state, bundleId)`（`js/src/shop/bundle-packs.js`）：扣 `cost` 金币、按 `contents` 批量把食材写进 `state.ingredients[id] = { qty, freshness:0 }`，照搬 `buyIngredient` 的 `stats.spent` / `seenIngredients` / `recordCatch` 范式；金币不足或食材 id 非法时返回失败。
- **展示组件** `BundlePacksPanel`：在「订购」面板（market iframe）顶部渲染，列出每个包的 emoji/名称/💰cost/内含食材与「购入」按钮；金币不足时按钮置灰为「金币不足」。
- **接线**：新增模块已加入 `app.bundle.js` 的 `TM_SOURCE_PARTS`（加载器模块数 53 → 54）；`IngredientMarketPanel` 的 `space-y-4` 首子插入 `<BundlePacksPanel state={e} commit={n} />`。

> 校验：浏览器无头实测进入订购面板 → 点 `btn-buy-bundle-basic` → 金币精确扣 50、成功提示含「基础烘焙包 / 低筋面粉」、可重复购买、0 pageerror。注意该面板位于跨文档的 market iframe 内，自动化测试需用 `frame_locator('iframe[data-testid="panel-frame-market"]')` 操作。

### 5.1 定价重平衡（修正早期倒挂）

早期 `cost` 全部高于"按单价散买"的总价（如基础包 50 > 33、达人包 120 > 86），导致补给包反而更贵、无性价比。已按 **九折批量优惠**重算（`新 cost = round(散买总价 × 0.9)`），全部低于散买价：

| 包 | 内含 | 散买总价 | 原 cost | **新 cost** | 省 |
|---|---|---|---|---|---|
| 基础烘焙包 | 低筋面粉×3·鸡蛋×3·糖×3 | 33 | 50 | **30** | 3 |
| 巧克力辅料包 | 黑巧克力×2·酵母×2 | 56 | 100 | **50** | 6 |
| 鲜果奶油包 | 草莓×3·淡奶油×1 | 65 | 110 | **59** | 6 |
| 达人烘焙包 | 低筋面粉×2·鸡蛋×2·黄油×2·淡奶油×2 | 86 | 120 | **77** | 9 |

> 单价取自 `INGREDIENT_MAP`：低筋面粉 6 / 鸡蛋 2 / 白砂糖 3 / 动物黄油 15 / 酵母 3 / 黑巧克力 25 / 淡奶油 20 / 草莓 15。若想调整折扣力度，改 `js/data/bundles/*.js` 里的 `cost` 即可（公式 = round(Σ 单价×数量 × 折扣率)）。

## 六、基础系统补全（手册双层架构 / 设置中心 / 引导 / 库存 / 数据清理）

按「还差哪些基础系统」的清单逐项落地。加载器 `TM_SOURCE_PARTS` 模块数 **54 → 56**（新增 `meta/main-story-system.js`、`a11y/system-dialogs.js`）。

### 6.1 A1：主线系统（双层架构）

需求：**玩家侧只展示"接到的委托 + 各种通知"（手册形式）；系统侧提供"只有系统可见"的主线系统**。据此做成两层：

| 层 | 载体 | 玩家可见 | 说明 |
|---|---|---|---|
| 系统内部 | `js/src/meta/main-story-system.js` → `window.Cake.mainStoryApi` | ❌ | 把 `QUESTS` 的 3 步（向镇长报到/学烤第一炉/办补贴）做成引擎：`seedHandbook` 开局播种、`advanceMainStory(state,key)` 推进、`mainStoryProgress` 查询。状态存 `state.mainStory.steps`，完成某步时**自动委托下一步**并推送通知 |
| 玩家可见 | `HandbookDialog`（📖 我的手册） | ✅ | 只显示 `state.handbook.commissions`（委托）与 `state.handbook.notifications`（通知）。玩家点「汇报完成」→ 内部调 `reportCommission`→`advanceMainStory`，主线在系统后台推进 |

- **状态落库**：`createNewGameState` 增加 `handbook:{commissions,notifications}` 与 `mainStory:{steps,version}`；读档流程 `seedHandbook` 幂等补种，兼容旧存档。
- **入口**：顶栏 `btn-handbook`（`TopBarToolRow`），主文档 Modal，不走 iframe。
- 主线步骤文案取 `window.Cake.QUESTS`（带兜底），完成委托会链式触发下一委托（连报 2 次 → 出现「办扶持补贴」委托），均已实测。

### 6.2 B1：统一设置中心

## 十、翻盖式竖折适配（v25 · moto razr 系列）

### 10.1 形态差异：与第九章不是同一类设备

用户补充说明真实设备是**竖版折叠屏、moto razr 系列**。第九章按「书本式横折」（Galaxy Fold 类，展开接近方形平板）设计，而 razr 是**翻盖式竖折（flip）**，形态相反：

| | 合盖外屏 | 展开内屏 |
|---|---|---|
| razr 2024 / 2025 | 3.6" `1056×1066`（近似正方形） | 6.9" `2640×1080`，**22:9 细长** |
| razr ultra 2025 | 4.0" `1272×1080` | 7.0" `2992×1224`，**22:9 细长** |
| 折算 CSS 视口（DPR 2.75~3） | 约 `352×355` ~ `424×360` | 约 `360×780` ~ `412×915` |

参数来源：[motorola razr 2024 官方规格](https://en-us.support.motorola.com/app/answers/detail/a_id/181495/~/specifications---motorola-razr---2024)、[razr ultra 2025 官方规格](https://www.motorola.com/ca/en/p/phones/razr/razr-ultra/pmipmhn40ms)、[PhoneArena 参数对比](https://www.phonearena.com/phones/compare/Motorola-razr-2024,Motorola-Razr-2025/phones/12380,12660)。moto 允许在外屏运行完整 App，所以合盖态是真实可玩的场景。

**关键结论**：展开内屏宽只有 360~412px，**根本不会触发第九章的 `fold` 档（≥641px）**；物理开合是「超矮近方屏 ↔ 细长竖屏」的连续尺寸变化，且不重载页面。第九章的三档方案对 razr 无害但也基本不起作用，真正的新场景是**合盖外屏**。

### 10.2 体检方法

Playwright 同一台 DPR3 触屏设备，8 个 razr 真实 CSS 视口 + 5 个非 razr 对照视口，逐项测量顶栏 / 页签 / 内容区高度、父与 iframe 的档位属性与字号、横向溢出、入口可达性；再加「合盖→展开→再合盖→再展开」动态序列、死锁复现、弹窗测量与截图人工核对。

### 10.3 发现的 4 个真实缺陷（改前实测）

| # | 缺陷 | 改前实测 | 根因 |
|---|---|---|---|
| 1 | **合盖外屏不可逆死锁（致命）** | 手动展开一次顶栏后，再合盖顶栏 **540px > 视口 355px**、内容区 **8px**，楼层卡片完全消失，且无法自动恢复 | `writeFlagPref` 把折叠键写进 localStorage，`auto-collapse.js` 的 `hasPref()` 把任何记录当成「用户手动选择」并**永久退出**自动逻辑 |
| 2 | **外屏手册 / 设置入口完全不可达** | 8 个视口中 4 个外屏 + 360×780 内屏均为 `btn-handbook=0 / btn-settings=0`，且无其他入口 | 顶栏收起时 `TopBarToolRow` 整行不渲染；而 `css/adapt.css` 的矮屏压缩写死 `orientation: landscape`，razr 竖向外屏不满足 |
| 3 | **展开内屏顶栏头重脚轻 + 360→393 宽度突跳** | `360×780` 顶栏 109px / 内容区 565px，`393×873` 顶栏 **495px** / 内容区 **273px**；仅差 33px 宽，内容区少 292px | `tight()` 的 `innerWidth<=360` 硬阈值让 360 宽自动收起、393 宽完全展开；22:9 细长屏恰好横跨 |
| 4 | **外屏可用空间被顶栏页签吃掉** | `352×355` 顶栏 109 + 页签 104 = 213px（60%），内容区仅 **141px**，楼层卡片文字竖排断字 | 缺少针对超矮屏的压缩规则 |

### 10.4 五档统一决策

`js/host/layout-sync.js` 升到 v25，新增两个互斥档位，仍由父页唯一决策并同步 `data-tm-*` 到所有 `panel-frame` iframe 文档（沿用 v23 教训，避免上下层判定分叉）：

| 档位 | 判据 | 用途 |
|---|---|---|
| `compact` | 粗指针 + 高 ≤440 | razr 合盖外屏、手机横屏等超矮触屏 |
| `wide` | 非粗指针 + 宽 ≥768 + 高 ≥560 | 桌面鼠标放大档（1080 列 / 32px，零回归） |
| `fold` | 粗指针 + 宽 ≥641 + 高 ≥560 | 书本式折叠展开 / 平板触屏（第九章） |
| `slim` | 粗指针 + 高 ≥700 + 高宽比 ≥2.05 | razr 22:9 内屏及普通细长竖屏 |
| `phone` | 其余 | 中等宽度竖屏、桌面窄窗口 |

优先级 `compact > wide > fold > slim > phone`；`phone` 不挂属性。四重触发（`resize` / `orientationchange` / `visualViewport.resize` / 250ms 轮询）保证物理开合不重载页面时也能实时换档。

### 10.7 伪缺陷澄清（避免复查误报）

- **「弹窗溢出不可滚」是测量对象错误**：`Modal` 卡片本身带内联 `maxHeight:78vh` + 子 `div.overflow-y-auto`，一直可滚动；首轮诊断量到的 `h=665` 是 `data-testid="handbook-modal"` 那个**内容 DIV 的自然高度**，不是卡片高度。本次只是把矮屏卡片从 78vh 提升到 `calc(100dvh - 12px)` 并减小 padding，属体验优化而非修 bug。
- **浮动入口不是只在 compact 档出现**：触发条件已扩展为「顶栏已渲染 + 处于收起态 + `btn-handbook` 不在 DOM」，因此 360×780 内屏、344×840 外屏、844×390 横屏也能访问手册 / 设置；顶栏展开后自动移除，不会与工具行重复。
- **`tight()` 的 `innerWidth<=360` 阈值刻意保留**：放宽会让 344 / 360 宽的既有自动收起行为变化，且与第八章「横屏→竖屏入口恢复」验收冲突；改由浮动入口兜底可达性，是改动面更小的解法。
- **脚本 ID 撞名**：`index.html` 初版给 `<script>` 设了 `id="tm-compact-entry"`，与 `compact-entry.js` 创建的浮动 DIV 同名，`getElementById` 先返回 script，导致 `build()` 永不执行且**无任何报错**。已改脚本 id 并加属性选择器防御。

- **razr 内屏铰链折痕、外屏摄像头挖孔**：属系统级硬件特征，CSS 层不处理；安全区仍由 `env(safe-area-inset-*)` 适配。

## 十二、顶栏胶囊横向重构（v27）

### 12.1 问题：不是设计意图，是布局退化

店主在真机「手机界面视图」（约 320 宽、特大字体）下指出：九个状态胶囊竖着排成一长列，而旁边那一小段店名文字反倒占了比九个胶囊加起来还大的空间；「为什么一定要让胶囊和胶囊列队、文字和文字列队」。

溯源结论：这是**按元素类型分两列 + 自动换行**导致的连锁退化，不是刻意设计。

| 位置 | 原实现 | 后果 |
|---|---|---|
| 顶栏展开态第一行 | `flex items-center justify-between`，三块并列：店名文字块（`min-w-0`，两行）/ 胶囊块 / 收起按钮 | 店名独占左侧一列，胶囊只能在右侧剩余宽度里排 |
| 胶囊块 `TopBarStatBadges` | `flex min-w-0 flex-1 flex-wrap items-center justify-end gap-1.5` | `flex-wrap` 一换行就变成 6+2 的参差断行；宽度再窄（320 + 特大字体）直接每行一个，塌成一长列 |
| 楼层总览 tab | `grid grid-cols-5 gap-1.5` | 390 宽下每列仅约 51px，特大字体（25.2px）时「1F 店面·厨房·工坊」被挤成 7 行逐字竖排 |
| 心情状态卡片 | 单行 `flex items-center` + 短句「耗精力会掉心情」 | 窄宽下短句被压成竖排 |

### 12.2 改法（只动容器，不动任何数据与玩法）

- **店名压成一行**：`街角甜品屋`（13px 加粗）`· 店主 小满`（11px），仍分得出主次，但不再占两行、不再独占一列。收起按钮留在这一行右端。
- **胶囊独占整行**：从 `justify-between` 的三块中拆出，作为下一行独立渲染；容器换成内联 `display:grid; gridTemplateColumns: repeat(auto-fit, minmax(86px, 1fr)); gap:5px; width:100%`。任何宽度下都按可用空间横向铺成整齐网格，**不存在换行塌成一列的路径**。每个胶囊加 `whiteSpace:nowrap`、`textAlign:center`、`display:block`，数值不折行。
- **楼层总览**：`gridTemplateColumns: repeat(auto-fit, minmax(104px, 1fr))` 覆盖 `grid-cols-5`，列数随宽度自适应，文字不再逐字竖排。
- **心情卡片**：外层 `flexWrap:wrap`，短句 `whiteSpace:nowrap`。
- 全部使用**内联 style**（本项目为自写 CSS，`whitespace-nowrap` 等 Tailwind 类无对应规则，v26 已踩过此坑）。

### 12.3 不改什么

九个玩法状态胶囊的**数量、含义、取值函数分档、emoji 全部不变**；六个时间胶囊、工具行、收起/展开机制、盲模式语音可达性、`tab-fate` 跳过逻辑、外屏 ☰ 菜单、v26 的浮层三级阶梯，一律保持。店名与店主的名称仍完整显示，只是合成一行。

### 12.4 校验结果

## 十三、无彩色 emoji 环境下的线性图标降级（v28）

### 13.1 需求与检测

店主提出：不支持 emoji 体系的浏览器应换用其他图标。此前四档实拍中，九个状态胶囊、六个时间胶囊、市场食材卡片等处的 emoji 全部渲染成空白方框（豆腐块）；而项目自带 `css/fonts/material-icons.woff2`（126KB），工具行与页签早已在用 `.material-icons` ligature。

检测只用 **canvas 像素法**：把 `🎉 🏅 🍓 💰` 画到 40×40 canvas，统计 RGB 通道差 > 24 的彩色像素；任一探针 ≥ 12 个彩色像素即判「支持」。`document.fonts.check('32px "Noto Color Emoji"')` 在本环境返回 `true`，但四个探针彩色像素全为 0，**不可靠，已弃用**。检测异常（拿不到 2d 上下文、抛错）时按「支持」处理，宁可不降级也不误伤。

### 13.2 图标来源：不猜名字，从字体反查码位

用 `fontTools` 解析自带 woff2 的 `GSUB` ligature 表 + `cmap`，反查得到 **2234 个「图标名 → 真实 PUA 码位」**。CSS 里写 `content: "\e227"`（码位来自字体自身），因此字形必定存在；若直接写 ligature 名，字体缺失时会退化成显示 `attach_money` 这类英文单词，比豆腐块更糟。

生成 `css/icon-fallback.css`：`292 条精准映射`（顶栏九状态、时间六项、手机 App 九宫格、常见食材/服饰/家具/天气/功能图标）+ `13 类 Unicode 区段兜底`（food/plant/animal/cloth/home/mood/travel/weather/doc/tool/award/heart/misc），未覆盖的 emoji 也有同类图标而非通用占位。生成脚本 `uicheck/gen_icon_css.py` 会校验每个图标名，缺失即报错，本次 0 缺失。

### 13.3 关键约束与实现

| 约束 | 做法 |
|---|---|
| 不能与共享作用域的 React 打架（历史白屏教训） | **只加属性、只改文本节点的 `nodeValue`**，绝不增删或移动节点 |
| 切回彩色表情要完整还原 | 原文本存在节点对象的 `__tmOrig` 上，恢复时写回；混合内容「🍬甜味」自然留下「甜味」 |
| iframe 由 React 动态创建 | 复用 `layout-sync.js` 的 `docs()` 模式，把 `data-tm-icon-line` / `data-tm-icon-style` 同步到父页与全部 `panel-frame`；MutationObserver + 400ms 定时补漏 |
| 裸文本 emoji（「🌙 关灯」「💰30」「📦 待送达」） | 删除装饰前缀，删后为空才留一个 `◆`；不碰 `✕ ✓ ⚠` 等文本符号 |
| 布局零漂移 | `::before` 用 `font-size: 1em` 跟随原字号，不用固定 `1rem`；宽屏顶栏维持 410px、手机 236px，与不降级态一致 |

**三档偏好**：`localStorage['sweet-icon-style']` = `auto`（默认，按检测结果）/ `emoji`（强制彩色）/ `line`（强制线性）。设置中心「显示」卡片增加三个按钮，CSS 用 `html[data-tm-icon-style=...]` 高亮当前档；暴露 `window.__cakeSetIconStyle(mode)`、`__cakeEmojiSupported`、`__cakeIconLine`。

### 13.4 两个实测踩坑（已修）

1. **CSS 隐藏规则被压过**：初版用 `html[data-tm-icon-line] .emoji[data-tm-e] { font-size: 0 !important }` 隐藏原 emoji，但 iframe 有自己的字体放大体系，实测 129 个已标注 span 的计算字号仍是 25.2px，方框与线性图标并排出现。改为直接把 emoji 字符从 `nodeValue` 摘除，彻底不依赖隐藏规则。
2. **注释里的 `*/` 吞规则**（项目第二次踩）：`css/icon-fallback.css` 顶部注释写了 `pages/*/index.html`，其中 `*/` 提前闭合注释，把紧随其后的基础 `::before` 规则整段吞掉 —— CSSOM 里只剩分类/精准映射规则，于是 `content` 生效但 `font-family` 丢失、图标显示不出来。改成「pages 各帧的 index.html」后 CSSOM 规则 0 恢复为基础规则。与 v24 书本式折叠那次同源。

另：裸文本 emoji 最初统一替换成 `◆`，实拍发现「◆材料补给包」「◆30」「◆文案墙」满屏菱形，比豆腐块还吵，改为删除装饰前缀。

### 13.5 校验结果

- `verify_v28.py` **30/30**：运行时三档切换、设置中心按钮点击、模拟「支持彩色 emoji 的浏览器」（mock canvas 彩色像素）、混合内容中文标签保留与还原、五个 `panel-frame` 全部加载 CSS / 同步属性 / 无漏标 / 无残留高位 emoji；全程 0 pageerror / 0 console.error / 0 失败请求。

## 十四、连续游玩一个月的 UI 修复（v29）

用交付包代码起本地服务，Playwright + Chromium 390×844 真实渲染，从第 13 天连续推进 30 天至第 56 天，逐日采集顶栏 / 弹窗 / 手册 / 数值并关键节点截图。30 天 0 报错、0 横向溢出、胶囊网格全程稳定，但暴露 8 处只在长玩后出现的问题，逐一修复：

1. **动态状态降级标注失效（v28 回归，最严重）**：`emoji-fallback.js` 只在节点首次出现时写 `data-tm-e` / `data-tm-ecat`，而状态表情随数值变脸（😄→🙂→🥱、💪→🤒、🍙→💫、天气/节气/星期也在换）时 React 复用同一 `<span>` 只换文本节点、不换属性，且 `spanSource` 优先读旧 `__tmOrig`。结果 D15 起 6 个胶囊「旧线性图标 + 空方框」并存、语义错配。修法：在 `markSpans` 里回收阶段检测 `nodeValue` 重新出现的 emoji，刷新 `__tmOrig` 后再按新文本重算 `data-tm-e` / `data-tm-ecat`；`textNodes` 的裸文本同理。D0/D15 `mismatch` 由 6 归零。

## 十五、死亡系统（v30）

需求：连续超过一周（7 天）不吃饭，店主**真死**。明确作为一个系统级机制落地，不是临时弹窗。

### 15.1 设计

- **计数器而非绝对天数**：`state.hungryDays` + `state.ateToday`。`advanceToNextDay` 跨天时：今天吃过 → `hungryDays=0`、`ateToday=false`；没吃 → `hungryDays+1`；`hungryDays>=7` 判 `dead=true`。最初用绝对天数锚点（`lastEatDay`），但老存档迁移会把 day 覆盖导致读档即误死，故废弃。
- **进食判定统一在 commit 层**：`useGameCommit` 比较本次 state 的 `satiety` 与上一帧基准，上升即认为玩家进食（做简餐 / 吃成品 / 苏记 / 快餐 / 美食街 / 捞金鱼 / 随机事件都表现为饱食度上涨），置 `ateToday=true`、`hungryDays=0`，避免逐入口打点遗漏。
- **真死不可复活**：`handleNextDay` / `handleSleepOvernight` 在 `dead` 时拦截推进。`DeathDialog` 常驻渲染、遮罩/Esc 关不掉。**默认只有一个「读档」按钮**（`btn-death-load`）回到死亡前的存活存档；**「重新开店」是冷静期选项**（`btn-death-restart`）——玩家在弹窗停留满 6 秒才浮现，防误触丢档。没有任何原地复活入口。
- **配套：存档时机改为仅跨天**：原 `useGameCommit` 每次操作都 `saveCurrentSlot`，死那一瞬也会把 `dead=true` 写盘，读档读出来还是死人。现移除 commit 内的存档，改为在 `useAutoSpeakDay`（跨天流程）里 `!l.dead` 时才存档；判死那天不写盘，磁盘因此始终保留最近一次**存活**的跨天存档，「读档」才有意义。手动存档（`useSaveGame`）、新游戏开局存档保留不变。「读档」回到的是最近一次跨天存档（`hungryDays` 可能已很高），玩家须尽快进食续命——这正是真死的惩罚。

### 15.2 修复的三个隐藏 bug

1. **存档丢失死亡字段**：`buildSaveMetaRow` 原只把 `satiety` 写进 `home` JSON，`hungryDays/ateToday/dead` 三个新字段既非独立列也未序列化，读档即归零。已在 `home` JSON 中补齐三者；`hydrateStateHome` 读不到时按 `0/false` 兜底，兼容老存档。
2. **读档后第一顿饭漏判**：`lastSatRef` 首帧只记基准不判断，读档后当天第一次进食正是首帧 commit，会被当成「没吃」。改为用 ref 同步当前存档 `satiety` 作为首帧基准（`baseSatRef`），第一顿也正确计入。期间修掉一次因声明链误加分号导致的 `u is not defined`（已还原为逗号链）。
3. **存档时机与真死冲突**：改为仅跨天存档后，进食不再立即写盘，`ateToday/hungryDays` 先存在内存 state、跨天时随存档落盘；验证方式相应改为「进食→跨天→读盘」而非进食后直接读盘。同步修正设置中心文案「每次操作后自动存档」→「每天跨天时自动存档」。

### 15.3 校验结果

- `verify_death.py` **15/15**：老存档推进不误死、连点 7 次恰好第 7 次死、真死无复活按钮、6 秒内重开未出现、满 6 秒浮现重开、死后无法推进、读档回到死亡前存活态、读档后不吃饭再跨天仍死、吃过后跨天清零、未进食满 7 天则死、0 报错。
- `verify_death_persist.py` **8/8**：推进 5 天落盘 `hungryDays=5`，读档保留，再推进至第 7 天准确死亡，0 报错。
- `verify_death_eat.py` **6/6**：读档后做简餐再跨天，`hungryDays` 6→0、未死，0 报错。
- 历史回归：`verify_v26.py` 33/33、`verify_v28.py` 30/30、`verify_v29_fixes.py` 13/13 全绿。

## 十六、心境死亡概率（v30 追加）

需求：死亡系统第二条路——中度抑郁每天结束时固定 3% 死亡率，重度抑郁 5%，双相 3%～10% 之间。测试时需使用修改器。

### 16.1 设计

- **复用既有心理系统**：`s.psych.dep` 本就分 0～3 级（心情 <40 连续 3 天转轻度、深陷 3 天或低落 8 天转中度、深陷 8 天转重度），`psych.bipolar` 为双相标志。此前只影响作息与恢复速度，从未致死；本夜接入死亡系统。
- **判定时机**：`advanceToNextDay` 里、饿死判定之后、`__tmPsychTick` 之前——用**跨天前的当日心境**掷骰。若用 tick 后的等级，中度可能当夜被降级/升级，3%/5% 的确定语义就会漂移。
- **费率**：`dep===2` 固定 3%；`dep>=3` 固定 5%；`bipolar` 每天在 `[3%,10%]` 区间内取一个费率再判（双相优先于抑郁等级，独立且更重的诊断）；`dep<=1` 不因心境致死。
- **优先级**：饿死（`hungryDays>=7`）先判，已死不再掷心境骰，死因归饿死。
- **死因字段** `deathCause`（`starve`/`psych`）：随 `home` JSON 存档/读档，老存档缺字段按 `starve` 兜底；死亡弹窗据此区分标题与正文（「店主饿死了」/「店主没能醒来」），真死流程（读档唯一即时出路、6 秒冷静期重开）两死因共用。
- **读档不治病**：`psych` 随存档保留，读档回到死亡前后心境仍在，下次跨天继续按同概率判定——想活必须治疗（提升心情/用药降级）。

### 16.2 测试修改器

按店主要求不靠真实随机碰运气，采用两层修改器：

1. **存档种子注入心境**：向 `home.psych` 写入目标 `dep/bipolar` 状态，读档即生效；
2. **`window.__CAKE_DEATH_TEST` 钩子**：`roll` 覆盖判定随机数、`bipolarRate` 覆盖双相当日费率（限幅在 3%～10%）。默认未设置时用 `Math.random()`，正常玩家不受影响。

### 16.3 校验结果

- `verify_psych_mortality.py` **25/25**：中度 3% 边界（0.02 死 / 0.029 死 / 0.031 活 / 0.04 活）、重度 5% 边界（0.04 死 / 0.049 死 / 0.051 活 / 0.06 活）、双相两端与中段（3% 端 0.029 死 0.031 活；10% 端 0.099 死 0.101 活；6.5% 中段 0.06 死 0.07 活）、双相优先于重度抑郁、轻度/正常心境 roll=0 不致死、死因文案区分、饿死优先、读档保留心境、0 报错。
- 死亡三套回归：`verify_death.py` 15/15、`verify_death_persist.py` 8/8、`verify_death_eat.py` 6/6。
- 历史回归：v26 33/33、v28 30/30、v29 13/13 全绿。

本次不删任何功能。

### 17.2 一处容易复发的坑

`panel-autofit.js` 原来用 `documentElement.scrollHeight` 设 iframe 高度。iframe 内 `.panel-area{height:calc(100dvh - 170px)}`、`#container{min-h-screen}`，而 iframe 里的 `100dvh` 就是**当前 iframe 高度**——于是每次测量都「内容 ≥ 当前高度 → 设更高」，高度只增不减。实测首页 iframe 被撑到 3004px（真实内容不到 2000px），滚到底是一大片空条纹。修法是双向的：`fit()` 只信 body / `#root` 的实测高度，iframe 内同时取消这两处视口高度依赖，高度才能随内容收缩。
